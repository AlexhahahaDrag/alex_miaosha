# RBAC 成熟度评审方案设计（机构 / 用户 / 角色 / 菜单 / 权限）

Date: 2026-08-06
Status: Approved（评审框架已确认，待执行评分）
Scope: 三端全量 RBAC —— backend `alex_miaosha_user`、PC `alex_miaosha_front`、mobile `alex_miaosha_mobile`
Branch: `develop-1.0-feature-org-manage`

## 1. 背景

RBAC 相关能力此前以「波次」方式推进，已落地三份 spec：

| Spec | 范围 | 状态 |
| --- | --- | --- |
| `2026-08-03-rbac-p1-wave1-design.md` | 后端：删除用户级联清理 + Org/Role 分页数据权限 | Implemented |
| `2026-08-03-rbac-p1-wave2-design.md` | PC：ID string 化 + 批量删除二次确认 + 用户列表筛选 | Implemented |
| `2026-08-03-role-assign-permissions-design.md` | 后端 + PC：角色权限批量分配接口 | Implemented |

问题不在于「没人发现缺陷」，而在于**每份 spec 的 Non-goals 段落各自沉淀了一批 follow-up，从未被汇总成一张带优先级的总账**。同时 PC 与 mobile 各有一份描述「目标态」的测试/设计文档（`docs/testing/rbac-stage1-midscene-test-design.md`、`docs/testing/mobile-rbac-visibility-checklist.md`），其描述的能力大部分尚未接到页面上，造成「文档态」与「代码态」脱节。

本 spec 定义一套可复现的评审框架，用于回答两个问题：**当前 RBAC 完善到什么程度**，以及**接下来按什么顺序改**。

## 2. 目标

1. 产出三端 × 全模块的成熟度评分卡，使「是否完善」有可横向对比、可复算的量化结论。
2. 产出缺陷登记册，使每个低分格子都能拆成带证据、成本、验收方式的可派活条目。
3. 汇总既有 spec 的 Non-goals 遗留项，避免重复发现与重复讨论。
4. 输出按风险分层的批次路线图，作为后续 writing-plans 的输入。

## 3. 非目标

- 不在本轮修改任何业务代码。本 spec 及其产出的评分卡、登记册均为只读评审成果。
- 不启动项目、不做运行时截图。视觉维度本轮基于代码静态审查（组件选型、样式值、交互态、与 `.cursorrules` 视觉基准对比）；实际截图留作后续批次的实施期验收手段。
- 不重写既有 stage1 契约文档。已被 `docs/superpowers/rbac-stage1-interface-contract.md` 覆盖的模块，直接引用其作为目标态。
- 不产出实现代码级方案。修复方向在登记册中只写一到两句，完整实现由 writing-plans 承接。

## 4. 基准线

目标态 = 业内中台 RBAC 成熟度基准 **∪** 仓内既有目标态文档。

| 来源 | 用途 |
| --- | --- |

两者冲突时以仓内文档为准，并在登记册中标注冲突点，供后续决策。

### 4.1 stage1 资产的分支归位

上表中 PC 的 stage1 契约与测试设计文档、以及 `src/components/rbac/*` 六个文件、`tests/midscene/rbac/cases/stage1-smoke.json`，原先只存在于 `codex/gift-management-module` 分支，在本评审分支上不可见。已按文件粒度取到本分支（前端仓 commit `3f3b605`，未携带任何 gift 业务代码），使基准线引用在本分支上可解析。

## 5. 评判维度与评分标准

### 5.1 维度与权重

| 维度 | 权重 | 覆盖内容 |
| --- | --- | --- |
| D1 安全与数据正确性 | 35% | 越权读写、数据权限漏挂、事务边界、唯一性与引用完整性校验、缓存一致性、敏感信息外泄 |
| D2 功能完整度 | 30% | 对标目标态应有能力是否存在（树、批量、启停、重置密码、差异预览、关系配置入口等） |
| D3 交互一致性 | 18% | 同端同类操作是否同款容器与同款反馈；三端同一能力口径是否一致；组件是否复用 |
| D4 视觉规范符合度 | 7% | 与 `.cursorrules` 视觉基准差距（加载态、空状态、卡片化、圆角、触觉反馈、侧距） |
| D5 可测性与回归保护 | 10% | 是否有能被 CI 执行的自动化测试；关键安全路径是否有测试；是否有自动化钩子；测试是否与实现对齐 |

权重来源：D1 > D2 > D3 > D4 为既定分层口径。D5 为追加维度，权重从 D3、D4 各让出一部分。

**D5 追加理由**：后端 `user_boot/src/test` 下有 4 个 RBAC 测试类（`OrgUserAssignmentServiceTest`、`RoleUserAssignmentServiceTest`、`UserPermissionContextServiceTest`、`MenuPermissionFilterTest`）写了测试方法但未挂 `@Test`，Surefire 实际不执行；PC `src/views/user/**` 无任何 `data-testid`，导致已写好的 `tests/midscene/rbac/cases/stage1-smoke.json` 缺少定位抓手；mobile 仓 `tests/` 目录不存在。若不独立计分，后续所有修复都缺少「改完不会坏回去」的保障，且修复本身无法验收。

### 5.2 通用分数锚点

| 分 | 语义 |
| --- | --- |
| 0 | 能力完全缺失 |
| 1 | 有雏形但不可用，或存在已知严重缺陷 |
| 2 | 基本可用，但缺关键保护或关键子能力 |
| 3 | 达到可交付底线 |
| 4 | 达到业内中台水平 |
| 5 | 优于基准，有额外保障 |

### 5.3 判据 checklist（决定分数，保证可复算）

每格得分 = 该维度判据勾中条数按下表折算。判据不适用时从分母中剔除，按剩余条数比例折算。

折算规则：勾中比例 0% → 0 分；(0%, 30%] → 1 分；(30%, 55%] → 2 分；(55%, 75%] → 3 分；(75%, 95%] → 4 分；(95%, 100%] → 5 分。

**判据选用规则（消除歧义）**：

- D1 有两套判据。backend 列的 7 格一律用「后端」判据；PC 与 mobile 列的全部 14 格一律用「前端消费侧」判据，不只是数据权限那两格。
- D2 第 9 条「导出能力」仅对 机构、用户 两个模块适用，其余模块该条从分母剔除。
- D4 按各端自己的 `.cursorrules` 评：PC 用 `alex_miaosha_front/.cursorrules`，mobile 用 `alex_miaosha_mobile/.cursorrules`；backend 列的 7 格 D4 全部不适用，直接记为 N/A 且从加权中剔除（该格权重按剩余 93% 归一化）。
- D4 第 4 条「触觉反馈」仅 mobile 适用。

**D1 判据（后端）**

1. 列表/分页查询挂 `@DataPermission` 且 scope 与列语义匹配
2. 详情查询（按 id）有数据权限或服务层归属校验
3. 写操作（增/改/删）有归属校验
4. 业务唯一字段有唯一性校验
5. 层级/引用完整性校验（父节点存在性、防环、删除前置保护）
6. 写操作处于显式事务边界内
7. 权限变更后缓存失效口径一致
8. 角色判定为精确匹配，非子串包含
9. 敏感信息不进日志、不出 VO
10. 单一模型无双轨写入口（不存在绕过约束的旁路 CRUD）

**D1 判据（前端消费侧）**

1. 实体 ID 全程 string，无 `Number(id)`
2. 存在按钮级权限校验（非仅路由级）
3. 前端不承担安全决策，仅做展示控制
4. 多角色权限码正确合并，非取首个角色
5. 写请求 payload 不回传只读字段

**D2 判据**

1. 基础 CRUD 完整
2. 列表筛选覆盖后端已支持的筛选字段
3. 服务端分页（非前端内存分页）
4. 批量操作（批量删除/批量启停）
5. 层级/树能力（模块适用时）
6. 状态启停有独立入口
7. 关系配置有专门入口且语义清晰
8. 目标态文档要求的能力已落地
9. 导出能力（模块需要时）

**D3 判据**

1. 同端同类操作容器一致（Modal 与 Drawer 不混用）
2. 危险操作有二次确认
3. 提交按钮有 loading 防重
4. 表单校验规则存在且覆盖必填项
5. 三端同一能力口径一致
6. 复用既有共享组件，无重复实现
7. 组件命名与项目规范一致

**D4 判据**

1. 加载态存在且优先骨架屏
2. 空状态有友好提示
3. 卡片化布局与圆角基准符合规范
4. 触觉反馈（mobile 关键操作）
5. 侧距与间距符合规范
6. 无 emoji 代替图标
7. 无残留调试输出与乱码文案

**D5 判据**

1. 存在自动化测试且能被 CI 实际执行
2. D1 类关键路径有测试覆盖
3. 存在自动化定位钩子（`data-testid` 等）
4. 测试描述的形态与当前实现一致
5. 测试可在本地一条命令跑通

## 6. 评分矩阵范围

7 模块 × 3 端 = 21 格，每格 5 个维度分，共 105 个分值。

| 模块 | backend | PC | mobile |
| --- | --- | --- | --- |
| 机构 org | 评 | 评 | 评 |
| 用户 user | 评 | 评 | 评（个人信息页，非管理页） |
| 角色 role | 评 | 评 | 评 |
| 菜单 menu | 评 | 评 | 评 |
| 权限点 permission | 评 | 评 | 评 |
| 关系配置（org-user / role-user / role-permission） | 评 | 评（仅 API，无页面） | 评（有页面，手填 ID） |
| 数据权限 data-scope | 评 | 消费侧 | 消费侧 |

### 6.1 两个特殊格子的处理

**PC 关系配置**：`src/views/user/{orgUserInfo,roleUserInfo,rolePermissionInfo}` 下仅有 `api/index.ts`，无页面；关系维护内嵌在用户表单与角色 Transfer 抽屉中。这不必然是缺陷（可能是有意的设计取舍），评分时记为「能力存在但入口分散」，由 D3 交互一致性承担扣分，不在 D2 记为能力缺失。

**数据权限的前端两格**：前端没有也不应有数据权限实现，故只评「消费侧正确性」——前端是否因误解后端过滤规则而做出错误假设。评分使用 D1 前端消费侧判据。

### 6.2 加权总分

单格总分 = Σ(维度分 × 权重) ÷ 5 × 100，取 0–100。

某维度整体 N/A 时（如 backend 的 D4），其权重按比例分摊到其余维度后归一化，再套上式。以 backend 为例：D4 的 7% 剔除后，其余四维权重变为 D1 37.6%、D2 32.3%、D3 19.4%、D5 10.7%（各自除以 0.93）。

端总分 = 该端 7 格加权平均。
模块总分 = 该模块 3 端加权平均，用于识别「哪个端拉后腿」。

因 backend 与前端的 D1 判据不同、backend 无 D4，**跨端比较仅在模块总分与单维度分层面有意义，单格总分不做跨端直接排名**。

## 7. 缺陷登记册规范

### 7.1 字段

| 字段 | 说明 |
| --- | --- |
| ID | `RBAC-<端>-<模块>-<序号>`，端取 `BE`/`PC`/`MB`，例如 `RBAC-BE-ORG-003` |
| 标题 | 一句话说清缺什么 |
| 端 / 模块 / 维度 | 回指评分矩阵格子与维度，保证登记册与评分卡双向可追溯 |
| 严重级 | S1–S4，定义见 7.2 |
| 证据 | 文件路径 + 行号范围，必须可点开验证 |
| 影响 | 谁会踩到、踩到后果 |
| 修复方向 | 一到两句，不写完整实现 |
| 成本 | S（半天内）/ M（一到三天）/ L（三天以上） |
| 验收 | 如何证明修好，优先写成可自动化断言 |
| 来源 | `新发现` 或既有 spec 的 Non-goals 引用 |

### 7.2 严重级定义

严重级决定批次归属，不等同于「重要程度」。

| 级 | 定义 |
| --- | --- |
| S1 | 可被利用的越权、数据错乱、静默数据丢失、敏感信息外泄 |
| S2 | 数据一致性风险、关键校验缺失、权限判定不可靠 |
| S3 | 功能缺失、目标态未落地、交互不一致 |
| S4 | 视觉与体验打磨、代码卫生 |

### 7.3 定级说明（评审执行时需遵循）

生产代码中的 `main` 方法打印密码定为 S1 而非 S4。它不属于代码卫生问题：一旦在生产环境被误触发或该类被反射调用，密码即进入日志。

## 8. 优化路线图

四个批次 + 一个前置批次，严格按严重级推进，不允许跨批次挑选低成本项——这是分层优先级口径的直接推论。

| 批次 | 内容 | 目的 |
| --- | --- | --- |
| 批次 0（前置） | 后端未挂 `@Test` 的 RBAC 测试类补注解并跑通；PC `src/views/user/**` 补 `data-testid` | 本身不修缺陷，但为后续三批提供回归保护与自动化抓手 |
| 批次 1 | 全部 S1 | 消除可被利用的越权与信息外泄 |
| 批次 2 | 全部 S2 | 收敛一致性风险与不可靠的权限判定 |
| 批次 3 | 全部 S3 | 补齐功能与目标态；需先确认产品形态 |
| 批次 4 | 全部 S4 | 视觉规范落地与代码卫生 |

### 8.1 批次 0 的必要性

批次 0 会将真正开始修 S1 的时间推迟约半天到一天。接受这个延迟，因为批次 1 修复的是数据权限与信息外泄类问题，其正确性无法靠人工点击验证；没有可执行的测试与定位钩子，批次 1 的「修好了」只能靠声明而非证明。

### 8.2 批次 3 的前置决策

批次 3 涉及 UI 形态变更。仓内 `tests/midscene/rbac/cases/stage1-smoke.json` 与 `docs/testing/rbac-stage1-midscene-test-design.md` 已描述一套目标 UI（用户页左机构树、机构 Drawer 契约、角色统计列、权限差异预览、独立的机构-用户与用户-角色配置页）。执行批次 3 前必须确认该设计是否仍然采纳，否则会出现「照旧文档改完又不满意」的返工。此决策点在登记册中显式标记为阻塞项。

### 8.3 验收方式

| 批次 | 验收手段 |
| --- | --- |
| 批次 0 | 测试实际被执行（用例数上升）；grep 确认 `data-testid` 覆盖目标页面 |
| 批次 1 | 自动化测试断言（数据权限 SQL 片段、越权访问被拒） |
| 批次 2 | 单元测试 + 集成测试 |
| 批次 3 | Midscene 用例通过 + 静态检查（共享组件是否真被引用） |
| 批次 4 | 静态检查 + 人工过一遍 |

## 11. 现状输入摘要

评审执行时以下列盘点结论为输入，评分需逐条复核证据而非直接采信。

**backend**：五模块 CRUD 与分页齐备；单用户唯一有效机构（`assignSingleOrg`）含并发锁与编程式事务；用户多角色与角色批量授权已实现；权限上下文含 Redis 缓存。薄弱点集中在详情查询无数据权限、机构无唯一性与防环校验、`OrgUserInfo` CRUD 与 `assignSingleOrg` 双轨、角色判定用子串包含、无树接口、测试未挂 `@Test`。

**PC**：五套 CRUD 列表 + Modal/部分 Drawer；权限树依赖 `src/compoments/menu-tree`；wave2 已落地 ID string 化、批量删除确认、用户筛选。薄弱点集中在 `src/components/rbac/*` 四个组件在库但零引用（详见 4.1）、stage1 目标 UI 未落地、无空状态与骨架屏、无 `data-testid`、菜单详情校验规则为空对象。
